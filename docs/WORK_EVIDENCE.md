# Анализ компетенций по рабочим примерам

Статус: этап 1 реализован — анализ синтетических рабочих примеров (`backend/app/evidence.py`, файл `demo/work_evidence_synthetic.json`). Живые интеграции GitHub/Jira/Confluence пока не реализованы. Подключения к аккаунтам не создавались, рабочие данные во внешние модели не отправлялись.

## Цель

Связать задачи, рабочие результаты, ревью и трудозатраты с конкретными компетенциями. Сотрудник получает объяснимую рекомендацию развития, а эксперт — факты для обсуждения. Оценка качества рабочего примера не равна оценке человека, его мотивации или основанию для кадрового решения.

Этот модуль дополняет профиль, историю обучения и требования грейда. Обязательный импорт JSON/CSV работает независимо от подключённых рабочих систем. Для хакатона используем синтетические задачи, PR, постановки и записи времени, отдельно от исходного датасета.

## Источники и подключение

| Источник | Что читаем | Вариант подключения |
| --- | --- | --- |
| GitHub | Изменения PR, связанные задачи, описание, ревью, комментарии, доступные результаты проверок | GitHub App с чтением выбранных репозиториев; первоначальная выборка через API, затем события и периодическая сверка |
| GitLab | Аналогичные merge requests, обсуждения и проверки | Отдельный адаптер GitLab REST API; не считаем его взаимозаменяемым с GitHub API |
| Confluence | Выбранные страницы, версии, разрешённые комментарии и ссылки на задачи | Confluence Cloud REST API v2, OAuth 2.0, ограничение разрешёнными пространствами и страницами |
| Jira | Требования задачи, критерии приёмки, история статусов, блокировки, оценки и worklogs | Jira Cloud REST API v3; учёт времени должен быть включён |
| Другой учёт времени | Подтверждённые записи по сотруднику и задаче | Адаптер конкретной системы после уточнения её API; для демонстрации импорт или собственная форма |
| CRM, helpdesk, тестовые и BI-системы | Рабочие материалы, соответствующие профессии | Отдельные адаптеры либо явный импорт выбранных материалов; продукты и права уточняются перед реализацией |

Git сам по себе хранит историю изменений, но не трудозатраты и полный процесс ревью. Для этого нужны платформа репозиториев и трекер задач. Время между коммитами не используем как отработанное время.

Для Atlassian в проектировании предполагается Cloud. Если банк использует Data Center, потребуется другая реализация подключения и проверки прав. Конкретные источники банка пока не подтверждены. Новые OAuth-приложения, webhooks и разрешения не регистрируются в рамках написания этой спецификации.

## Где сотрудник отмечает время

Если организация уже использует Jira или отдельную систему учёта, она остаётся источником времени. Не требуем повторного ввода в Career Quest. При отсутствии системы добавляем простую форму: задача, дата, длительность, вид работы и необязательный комментарий о препятствии. Таймер может помогать, но запись подтверждает сам сотрудник; наблюдение за экраном и клавиатурой не требуется.

Разделяем реализацию, анализ, тестирование, ревью, исправления и взаимодействие по задаче. Ожидание согласования или внешнего сервиса хранится как блокировка календарного процесса, а не автоматически как активная работа. Длительность процесса, записанные трудозатраты и оценка задачи — разные показатели.

Сопоставление «план/факт» даёт контекст для разговора, но не доказывает недостаток навыка. Учитываем изменение требований, сложность, исследовательский характер работы, совместное авторство и помощь коллегам. Отсутствие worklog означает отсутствие данных. При синхронизации сохраняем изменения и удаления; не суммируем одно время из Jira и дублирующего его экспорта. Story points не переводим в универсальные часы и не сравниваем как норму разных команд.

## Профессии и критерии

Критерии утверждает профильный эксперт; LLM может подготовить черновик. Анализируем сильные стороны и области развития. Число документов, коммитов, найденных багов или закрытых обращений не превращаем в рейтинг компетентности.

| Профессия | Рабочие примеры | Предлагаемые критерии |
| --- | --- | --- |
| Backend Engineer | PR, тесты, API-контракты, проектные решения, задачи | Обработка ошибок, проверки доступа, тестирование границ, контракт API, обоснование решения |
| Frontend Engineer | PR, компоненты, UI-проверки, требования задачи | Состояния загрузки и ошибок, доступность, типизация, тестирование поведения, производительность с учётом измерений |
| QA Engineer | Тест-кейсы, автотесты, баг-репорты и требования | Покрытие рисков и границ, воспроизводимость, качество проверок, связь с критериями приёмки |
| Data Analyst | SQL, ноутбуки, отчёты и определения метрик | Проверка данных, корректность агрегаций и знаменателей, воспроизводимость, ограничения вывода |
| Product Manager | PRD, гипотезы, планы экспериментов, решения о приоритетах | Ясность проблемы, критерии успеха, проверяемость гипотез, обоснование компромиссов |
| HR Business Partner | Обезличенные планы онбординга, программы развития и регламенты | Ясность процесса, измеримые цели, связь компетенций и обучения; чувствительные кадровые дела исключены |
| Sales Manager | Обезличенные записи CRM и согласованные примеры предложений | Выявленные потребности, аргументация, следующий шаг, качество фиксации; объём продаж не является самостоятельной оценкой навыка |
| Customer Support Specialist | Обезличенные обращения, ответы, база знаний и QA-ревью | Полнота решения, корректность инструкции, ясность объяснения, уместность эскалации с учётом сложности |
| Business Analyst — новая роль | Постановки Confluence/Jira, схемы процессов, сценарии | Однозначность требований, бизнес-правила, критерии приёмки, исключения, согласованность и трассируемость |

Business Analyst отсутствует среди восьми исходных ролей. Добавляем его отдельным расширением каталога с требованиями по грейдам, утверждёнными экспертом. Уже существующий `SK_REQUIREMENTS` можно использовать вместе с релевантными навыками коммуникации и работы со стейкхолдерами. Не подменяем Business Analyst ролью Data Analyst. Новые роли и дополнительные мероприятия храним отдельно; исходный стартовый набор остаётся неизменным.

## От материала до рекомендации

1. Администратор выбирает источники, проекты и период анализа. Подтверждённая таблица идентичностей связывает внешний ID с `employee_id`; совпадения имени недостаточно.
2. Связываем задачу с PR и документом через явную ссылку или ключ задачи. Неоднозначные связи и совместное авторство помечаем для проверки; неизвестного автора не назначаем предположением.
3. Сохраняем версию материала, разрешённые фрагменты и контекст: цель задачи, критерии приёмки, ограничения, значимые изменения и проверенный вклад сотрудника.
4. Правила и инструменты собирают наблюдаемые факты. Например, проверка тестов или критериев приёмки требует содержимого соответствующих материалов: одного отсутствующего файла в diff недостаточно.
5. LLM получает ограниченный набор рабочих примеров и критерии для профессии. Она возвращает сильные стороны, конкретные наблюдения, возможные области развития, ссылки на доказательства, альтернативные объяснения и недостающий контекст. Файлы и комментарии рассматриваются как данные, а не команды модели.
6. Сервер проверяет ссылки, существование навыков и соответствие версии материала. Повторные комментарии к одной задаче не считаются независимыми доказательствами. Субъективное замечание ревьюера не считается автоматически установленным дефектом.
7. Сотрудник видит анализ и может добавить контекст или оспорить наблюдение. Профильный эксперт подтверждает либо отклоняет его; только подтверждённая оценка по утверждённым критериям может изменить оценённый уровень навыка.
8. Движок рекомендаций связывает подтверждённые области развития с карьерной целью и доступным каталогом. Пока наблюдение не проверено, можно предложить добровольную диагностику или обучение с явной пометкой неопределённости, не снижая подтверждённый уровень.

Для каждого наблюдения храним навык, критерий, автора/вклад, период, число независимых примеров, ссылки и версии, ограничения анализа, версию модели и промпта, статус проверки и объяснение эксперта. Отдельно сохраняем проверенные сильные стороны. При неполных данных результат — «недостаточно сведений», а не нулевой навык. Уверенность модели не выдаём за статистически проверенную вероятность.

Не вводим формулу «10 часов = низкий уровень» или «три замечания = минус балл». Продвижение по правилам обучающего датасета, подтверждённая оценка и предварительное наблюдение AI остаются различными сущностями. Изменение оценки не должно повторно начислять прирост уже учтённых курсов. AI не принимает решения о повышении, оплате, увольнении или выдаче награды. Награды остаются в отдельном процессе с одобрением HR.

## Примеры демонстрации

**Разработчик.** В нескольких синтетических задачах после проверки контекста повторяется отсутствие обработки одного типа ошибки. Система показывает конкретные версии PR и замечания, отдельно отмечает сильные стороны, предлагает проверить навык тестирования API и подходящее обучение. Долгое ожидание ревью не приписывается недостатку навыка автора.

**Бизнес-аналитик.** В нескольких синтетических постановках отсутствуют согласованные сценарии отказа и проверяемые критерии приёмки. В отчёте есть ссылки на версии и конкретные фрагменты; сотрудник может указать связанный документ, где сценарий уже описан. После проверки эксперт подтверждает область развития `SK_REQUIREMENTS`. Для новой роли курс должен иметь утверждённую аудиторию; нельзя автоматически рекомендовать закрытый для неё курс другой профессии.

В обоих случаях вывод не строится на стиле письма, языке, количестве текста или одном спорном примере. Примеры выше иллюстративные и не являются результатами анализа реальных сотрудников.

## Права и обработка данных

Коннекторы читают только разрешённые проекты и материалы. HR-доступ не означает доступ ко всему исходному коду, клиентским обращениям или кадровым документам. Сотрудник видит свой разбор; назначенный эксперт — разрешённые ему материалы; HR — согласованные выводы и агрегаты в рамках своих прав. Права и источник сохраняются и для производных результатов; скрытая ссылка не делает цитату из закрытого документа общедоступной.

Секреты, клиентские данные, личные переписки и сведения о здоровье не входят в анализ. Реальные внутренние материалы банка нельзя автоматически отправлять во внешний LLM API: перед пилотом согласуются допустимые категории данных, доступ, хранение и место обработки. До этого работаем с синтетическими примерами. Замена имени идентификатором не обезличивает содержимое всего документа.

Сотруднику видны источники, критерии и способ исправить неверную привязку. Пересмотр или удаление источника и отзыв доступа приводят к пересчёту/закрытию соответствующих производных материалов. Не собираем скрытые сведения о действиях на компьютере и не выводим психологические характеристики из рабочего поведения.

## Техническая интеграция

Основной стек остаётся прежним: FastAPI, PostgreSQL, PydanticAI и OpenAI Responses API. Добавляем адаптеры источников, схемы нормализации Pydantic и таблицы `connections`, `external_identities`, `work_artifacts`, `task_contexts`, `worklogs`, `skill_observations`, `assessment_reviews`.

Для синхронизации и анализа нужен отдельный Python worker. В пилоте очередь заданий можно хранить в PostgreSQL: фиксировать статус, попытки и аренду задания, обеспечивать повторяемость по ключу «источник + объект + версия». Webhook при наличии быстро регистрирует событие после проверки подлинности, обработка выполняется вне HTTP-запроса. Периодическая сверка покрывает пропущенные события, изменения и удаления с учётом пагинации и ограничений API. Недоступность источника отображается как устаревшие данные, а не отсутствие работы.

LLM анализирует только изменённые разрешённые материалы с необходимым контекстом. Результат кэшируется по версиям материала, критериев, модели и промпта. Для большого набора исходный анализ асинхронный; интерфейс быстро показывает статус и последнее актуальное состояние. Лимит 10 секунд для пользовательской рекомендации не означает, что вся история репозитория будет обработана за 10 секунд. На старте векторная база и отдельный Redis не требуются.

## Объём реализации

1. Сохранить обязательный сценарий ТЗ на исходных профилях и истории обучения.
2. Добавить синтетический комплект из связанных задач, PR, постановок и времени для разработчика и бизнес-аналитика; показать анализ, проверку экспертом и рекомендацию.
3. Реализовать GitHub, Jira и Confluence для выбранных тестовых проектов с явным доступом и сопоставлением аккаунтов. Без тестового пространства разрешённый импорт демонстрирует ту же схему, но не выдаётся за живое подключение.
4. Расширять адаптеры и критерии на остальные профессии после проверки первых сценариев. Не заявлять все системы подключёнными на основании одной таблицы адаптеров.

Проверки: неверная привязка аккаунта; совместное авторство; исправленное замечание; неполный diff; дубликат/удаление worklog; блокировка вместо активной работы; отсутствие доступа; повторный webhook; неподтверждённое наблюдение не меняет навык; неполные данные не снижают оценку; инструкция внутри документа не меняет поведение анализа; отзыв доступа закрывает производные фрагменты.
